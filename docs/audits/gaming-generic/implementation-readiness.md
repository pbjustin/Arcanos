## Architecture and compatibility

The existing hybrid-v2 workflow remains the authority for acquisition, candidate admission, actor scope, revisions, idempotency, TTLs, budgets, evidence selection, and terminal outcomes. Explicit v1 compatibility remains. Source acquisition still uses the protected resolver; source access denial, unsafe redirects, sensitive URLs, instruction-bearing evidence, provenance failures, and source-use restrictions retain their existing controls.

`selectGamingGameScopedDocument` in `gamingStructuralEvidence.ts` separates intact parser-owned local gameplay records from source-global declarations. Unrelated local records and bounded reference blocks can be excluded from selected evidence. Contradictory primary subjects, conflicting global Game metadata, incomplete or ambiguous scope, and incompatible editions remain rejected or unverified. Projection preserves the original acquired artifact and hash; accepting projected gameplay evidence does not authorize whole-page storage.

`gamingGameRegistry.ts` consumes bounded, reviewed literal identity data: canonical IDs, aliases, related titles, editions, expansions, platforms, provenance, schema and revision. Generic validators consume relationships rather than named-game branches. Formatting normalizers and stored identity keys remain compatible; legacy named exports remain wrappers. Registry membership supplies recognition context, never source authority or independently acquired identity. Unknown games can satisfy the acquired-title/body or intact locally declared gameplay path; a request name, URL, duplicate title/H1, or publisher hint cannot establish that agreement. [Registry review requirements](registry-design.md) govern additions.

`gamingSourceEvaluation.ts` adds an internal versioned ledger for acquisition, extraction, identity, applicability, relevance, freshness, authority, selection, and generation readiness. Each stage has an explicit status, closed reason code and bounded fields. Definitive rejected or interrupted evaluations cannot be overwritten by later success. Candidate and workflow logs retain opaque correlations, counts, versions and terminal/recovery facts; they exclude publisher passages and raw user requests. Public workflow contracts and established reason projections remain compatible.

`assessGamingClaimCorroboration` compares only intact supported structural assertions in the actual selected backend evidence. Scope includes acquired game, edition, patch and platform, with prior identity/applicability gates. The optional versioned summary distinguishes independent, single-source, conflicting and unverified reports. Reviewed publisher-family data groups affiliated pages; exact copied reports connect publication lineages transitively. Unknown ownership earns no independence credit. It does not establish factual truth or in-game observation.

The corroboration summary adds CLEAR warnings only. It changes no score, acceptance gate, selected passage, provider prompt, source policy or required qualification. Existing full-pool conflict checks precede compaction. `runGameplayPipeline` still checks selected evidence before provider dispatch, audits the exact qualified answer, and returns a server-only bound answer assessment. The final hybrid gate rechecks evidence/answer fingerprints, attribution membership and citation targets. Unsupported claims therefore receive no new path around the existing generation gates. Semantic correctness still depends on the existing answer audit and separately validated generation path.

## Evidence and remaining release gaps

[The benchmark report](benchmark.md) defines 140 fixed candidate evaluations: 45 valid and 95 invalid, across three unrelated known games, two unregistered invented games, and multiple layout shapes. The immutable candidate recorded there accepts 45/45 valid cases and rejects 95/95 invalid cases; false-negative and false-positive rates are each 0%, structured coverage is 140/140, and security-critical invalid admissions/foreign-record sentinels are zero. The pristine baseline is 40/45 valid accepted and 85/95 invalid rejected. Labels were specified and separately reviewed internally, not through a blinded external study.

These are finite correlated synthetic observations. Nominal 95% Wilson lower bounds are 92.13% for acceptance and 96.11% for rejection, so this corpus does not establish population targets of 95% and 99%. Representative independent labels, broader source layouts, live access and generation evidence remain separate gaps. Candidate-only diagnostic coverage explicitly leaves generation unevaluated.

Focused corroboration, selected-evidence handoff, parser and compatibility checks have passed locally with Node 24.18.1/npm 11.16.0. Handoff tests retain protected mocked acquisition/extraction/selection and deliberately stop before the provider. Final full-suite, security, build/lint/type, private-plugin, disposable PostgreSQL and exact-head CI results must be taken from the validation ledger; intermediate failures or skipped paths remain failures or skips until recorded revalidation closes them. Earlier concurrent-tree results cannot attest the final committed implementation.

Hosted sealed Railway preview is **not run: draft admission unsupported**. The supported lifecycle requires `draft=false`; the user requires stopping at draft PRs. Offline sealed graph/import and fixture checks remain useful component evidence, but the admission gate must not be weakened and the PR must not be promoted to bypass it. Neither an old preview nor synthetic success proves live publisher reacquisition or Trinity generation.

The source-family registry needs owner provenance review. Recognition, source authority, licensing/storage policy and publisher ownership remain separate review decisions. No production variables, credentials, services, release holds, merges, deployments, access controls or paid provider calls are authorized by this task.

## Risks and rollback

The main compatibility risk is conservative identity or edition behavior causing additional unknown/clarification outcomes. Retain negative controls for source-global conflict, malformed local declarations, DLC/platform scope and unknown-title identity; investigate false rejections with bounded stage diagnostics rather than acceptance exceptions. Policy v2 deliberately invalidates old quality decisions; this may require reevaluation of existing stored records and can reduce temporary availability. It does not authorize reacquisition or storage contrary to source policy.

Before any separately authorized rollout, preserve the reviewed registry and rule versions and deploy the agreed code/data together through the protected release workflow. Roll back code and recognition data as one tested set; do not restore cached current-policy assessments into an older context, waive final answer audit, or toggle security gates. Process-local caches can be discarded by the normal process replacement. Immutable stored source revisions remain available to existing repository revision mechanisms, but reactivation requires current acquisition/source-policy/CLEAR eligibility. No destructive database migration is part of this candidate.

Optional corroboration can be reverted independently after removing its handoff and warning integration; existing answer eligibility should remain unchanged. A foundation rollback reintroduces the reproduced source-scope defects and must therefore retain the documented regression risk. No production rollback is performed or authorized here.

Production-readiness verdict: **NOT READY**. The work is a controlled candidate for private draft review. Exact-head release evidence, applicable final gates, publisher-family review and the stated live/representative validation gaps remain separate from local regression success. Merge and production promotion require additional owner authorization.

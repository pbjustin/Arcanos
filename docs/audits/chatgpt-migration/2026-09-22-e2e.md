## Full-suite CI failure and controlled reproduction

Both original-head [CI/CD](https://github.com/pbjustin/Arcanos/actions/runs/35812567182)
and [PR CI](https://github.com/pbjustin/Arcanos/actions/runs/35812567198) failed
only the first MCP SDK lifecycle case. Each reported 782 passing suites,
one failed suite and 13 skipped suites; 13,681 passing tests, one failure and
167 skips. The call received `TUTOR_UNAVAILABLE` before its execution fixture.

Safety state is read from `memory/safety-runtime-state.json` at module import.
The MCP test reset it only after each case, so the first case could inherit a
blocking condition persisted by another test. In a separate disposable
checkout, seeding a synthetic integrity block before importing the original
suite reproduced the same HTTP failure. Adding a before-each reset made that
same seeded run pass. The real unsafe-runtime denial case also passed; no
production guard was changed or disabled.

The reusable seed is
[`chatgpt-inherited-safety-state.json`](../../../tests/fixtures/chatgpt-inherited-safety-state.json).
For this reproduction only, copy it to `memory/safety-runtime-state.json` in
a separate disposable checkout with no existing runtime state, then run:

```text
node scripts/run-jest.mjs --runTestsByPath tests/chatgpt-mcp.integration.test.ts --testNamePattern="runs real SDK initialize|preserves runtime safety denial" --runInBand --coverage=false
```

Never overwrite a user's runtime state to run this fixture. The normal suite
does not install the seed; the explicit control demonstrates why initial test
state matters independently of full-suite ordering.

## Ingress and identity fixtures

The real MCP router suite now contains 36 passing cases. New coverage verifies:

- Rotating `X-Forwarded-For`, forged `X-Real-IP` and forged edge headers cannot
  evade the pre-authentication limit from an untrusted socket, with either
  Railway trust setting.
- A simulated trusted Railway socket receives separate real-client buckets
  only when the existing trust setting permits it. Forwarding-header changes
  never reset the original client's exhausted bucket.
- Thirty-one independently signed tokens for the same subject share one
  principal limit. A different subject retains access. Discovery charges no
  provider admission, and an exhausted subject cannot invoke the tool.

These cases exercise the route's actual identity policy. Simulating a socket
peer is not proof of deployed TLS, DNS, ingress headers or platform routing.

## Assembled backend end-to-end proof

All eight cases in
[`chatgpt-tutor.e2e.integration.test.ts`](../../../tests/chatgpt-tutor.e2e.integration.test.ts)
passed. They use a real MCP SDK client over HTTP, real `createApp`, the production
remote-JWKS JWT verifier, `executeTutorPilot`, Tutor, Trinity, HRC, the actual
OpenAI adapter singleton and the real OpenAI SDK's Responses HTTP transport.
The route, execution adapter, authentication, provider mapping and generation
pipeline are not mocked.

The [upstream fixture](../../../tests/fixtures/chatgpt-tutor-e2e.ts) serves real
loopback HTTP JWKS and Responses endpoints. It derives answers solely from the
observed provider request body. Each success test creates an unpredictable
marker; neither the fixture nor the application receives that marker out of
band. Assertions match the final structured answer, text output and canonical
output schema, and verify that both generation and HRC receive the expected
content. Discovery retrieves and caches the signing key without generation.

| Scenario | Result |
| --- | --- |
| MCP initialize, initialized, list and call through the full backend | PASS; prompt marker survives every layer and provider/HRC calls are observed |
| Concurrent subjects using the same supplied transport session header | PASS; each receives its own marker, and a later question receives neither prior marker |
| Inherited backend session history | PASS; a separate private marker never reaches provider input |
| Malformed, wrong audience, expired, forged and insufficient-scope tokens | PASS; fixed 401/403 response before provider execution |
| Unadvertised tool, extra session argument, runtime/control and memory-inspection prompts | PASS; rejected before provider execution |
| Provider HTTP 500 with private diagnostic | PASS; fixed unavailable error, no structured success or mock answer |
| HRC HTTP failure with private diagnostic | PASS; private diagnostic absent from the completed Tutor response |
| Actual HTTP client disconnect | PASS; pending provider socket closes, no later HRC or completed lineage |
| Actual production 60-second aggregate deadline | PASS; `TUTOR_TIMEOUT` after about 60 seconds, provider socket closes, no partial result |

All observed provider calls have `store:false`, even though the fixture sets
the default to true. Backend memory, session persistence, RAG, scholarly access,
database pool use and optional feedback/self-improvement sinks fail if called.
Raw prompt content is absent from the intercepted lineage calls.

Startup initialization and diagnostics are replaced to prevent background
services. Prohibited storage/retrieval and optional-effect sinks are fixtures;
lineage is intercepted for assertions. The exact synthetic HTTPS JWKS identifier
is mapped to loopback HTTP, and fetch destinations are restricted to the test
listeners. The adapter uses a synthetic key with SDK retries disabled. This
proves backend composition and HTTP mapping, not TLS, real issuer registration,
consent/refresh, model quality or installed ChatGPT behavior.

Run the assembled proof with:

```text
node scripts/run-jest.mjs --runTestsByPath tests/chatgpt-tutor.e2e.integration.test.ts --runInBand --coverage=false
```

The deadline case deliberately takes one minute; its test timeout is 70 seconds.
It also asserts at least 59 seconds elapse, so an incorrectly shortened deadline
cannot satisfy the test. The strengthened case passed in 60,070 milliseconds.

## Sensitivity to deliberately broken source

An independent reviewer ran the success case in a separate control checkout:

1. The unchanged source passed.
2. Replacing only the prompt forwarded into `ArcanosTutor.actions.query` with
   unrelated fixed text failed the final answer assertion: the unpredictable
   marker was absent and the fixture returned its no-context answer.
3. Restoring that source and removing only `disableMemoryAccess: true` from
   isolated Tutor options failed both the success assertion and the forbidden
   storage assertion. The real pipeline attempted a memory read.
4. Restoring the original source bytes made the same success case pass again.

The reviewer also changed only the route's deadline from 60,000 to 1,000
milliseconds in the control checkout. The strengthened deadline case failed
its elapsed-time assertion at 1,018.95 milliseconds, as intended.

All three source files were restored with matching SHA-256 hashes and an empty
source diff. The primary worktree was never mutated for these controls. These
expected failures demonstrate that the proof detects lost input propagation,
lost memory isolation and a shortened deadline.

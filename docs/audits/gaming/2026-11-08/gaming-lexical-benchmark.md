# Gaming lexical selection benchmark

This dated synthetic benchmark measures the production stored-evidence selector,
formatter, request-coverage assessor and deterministic CLEAR evidence gate. It
does not measure PostgreSQL full-text query execution/ranking, network retrieval,
Trinity prose generation, final-answer semantic auditing or live-provider quality.
All candidate ranks are fixed at one to isolate the post-query selection policy.
No embeddings, model calls, database, new dependencies or external requests run.

Baseline: `eea2d0b6ed72d00e3489a9f8ddf45335b3aa1e86` (merged #1591–#1594).
Runtime: Node 24.18.1 / npm 11.16.0, native Windows, in-band Jest.
The [raw before/after receipt](gaming-lexical-benchmark.json) records every query,
selected record label, quality result and resource observation. Revision
and source URLs are asserted against the original fixture rows, rather than
inferred from a citation string. The corpus has 15 authored records, 15 labeled
questions, three known games and one unfamiliar synthetic game.

## Reproduced selection failure and repair

For an explicit base-game equipment-load question, a shorter DLC prose passage
could displace the compatible base-game passage during v2 minimum-cost coverage
selection. Both rows were in the bounded pool and had positive equal lexical
ranks. The source's content-bound applicability and server-owned edition said
DLC. The request-coverage assessor found topic support, but the unchanged CLEAR
gate rejected the resulting set for incompatible edition. Thus this was an
answer-availability defect; the baseline did not authorize a wrong-edition answer.
Legacy selection also retained the incompatible prose passage beside the valid
one, exposing the set to the same final compatibility veto.

The repair adds one preselection check in
[gamingStoredEvidenceCore.ts](../../../../src/shared/gaming/gamingStoredEvidenceCore.ts),
using the existing request-edition resolver and edition-compatibility predicate.
It applies when both source and requested edition are present. It does not fill
missing player scope, normalize new edition aliases, weaken CLEAR, or change SQL,
authority assessments, ingestion grants, acquisition budgets or public schemas.

The permanent regression suite failed **4 assertions / passed 9** with only the
new prefilter removed, reproducing original selector behavior with the final
fixtures. Restoring the prefilter passed **13/13**; the companion existing stored
source-scope suite passed **39/39**. Source swaps were local, scoped to the new
four-line filter and restored in a `finally` block before integration validation.

## Before/after quality

Recall and precision are macro averages across all 15 questions. Recall@3 is
relevant returned passages divided by all independently labeled relevant passages.
Precision@3 uses a fixed denominator of three, counting unused slots; it therefore
does not reward padding the answer with redundant sources. Pooled returned
precision separately measures precision among the passages actually returned.
Every request limits selection to three passages. Exact labels describe authored
fixture semantics, rather than being generated by the retrieval implementation.

| Metric | Baseline | Repaired |
| --- | --- | --- |
| Recall@3 | 80.00% | 86.67% |
| Precision@3, fixed three slots | 31.11% | 33.33% |
| Pooled precision of returned passages | 93.33% | 100.00% |
| Exact-mechanic retrieval | 8/8 | 8/8 |
| Paraphrase retrieval | 2/4 | 2/4 |
| Complementary two-source request coverage | 2/2 | 2/2 |
| Deterministic request-coverage proxy | 12/15 | 12/15 |
| CLEAR evidence acceptance proxy | 11/15 | 12/15 |
| Wrongly authorized distractor sets | 0 | 0 |
| Selected original URL/revision/fetch-time integrity | 100% | 100% |

Request coverage alone was already positive for the incompatible DLC passage;
the change makes that request both relevant and compatible instead of increasing
the coverage proxy artificially. CLEAR acceptance here is evidence eligibility,
not a generated-answer correctness score. The CI path also checks that isolated
foreign-game, foreign-edition, foreign-platform, unverified, reference-only and
revoked records cannot become selected answer evidence. A separate old-patch
control rejects the known mismatched patch, and the surviving row still produces
`clarify` when independent currentness proof is absent.

## Resource observations

Each sample is a batch of all 15 queries through selection, formatting, coverage
and CLEAR. The report retains five repeat samples and CPU/heap/process metrics.
Inputs, selections and quality outcomes must repeat exactly; timing and memory
have no unstable pass threshold.

| Observation | Baseline | Repaired |
| --- | --- | --- |
| Batch median | 33.85 ms | 33.17 ms |
| Batch maximum, five samples | 36.62 ms | 37.67 ms |
| User/system CPU across samples | 171/63 ms | 203/32 ms |
| Heap delta | +19,116,840 bytes | -1,824,048 bytes |
| Process maximum RSS, including Jest | 180,032 KiB | 183,372 KiB |

These short runs are observational, include test-runner overhead and concurrent
machine scheduling, and do not establish a speedup or memory improvement. Heap
collection explains why a delta may be negative. They do not measure SQL index
size, SQL lookup latency, network latency or production memory consumption.

Reproduce the current report from repository root after the required shared
package build, with the pinned toolchain:

```powershell
node scripts/run-jest.mjs --runTestsByPath tests/gaming-lexical-retrieval-benchmark.test.ts --coverage=false --runInBand --silent=false --verbose
```

The report prefix is `GAMING_LEXICAL_BENCHMARK_REPORT`. Fixture inputs and independent
labels live in
[gamingLexicalBenchmarkFixtures.ts](../../../../tests/testUtils/gamingLexicalBenchmarkFixtures.ts).
The baseline behavior can be reproduced in a separate checkout of the recorded
base with these same fixture/test files. Expected permanent regression failures
must remain visible; do not revise the labels to make the old selector pass.

## Phase 3 proposal, separate from this PR

This small corpus demonstrates a retrieval gap, but does not yet demonstrate that
embeddings outperform bounded lexical improvements. “Why does dodging feel
sluggish?” finds no equipment-load passage; “unlock the entrance” finds no
gate-opening passage. “Restore the damaged crossing” retrieves the bridge row
through one overlapping word but fails the unchanged claim-coverage gate. Of the
four paraphrases, only the poise/interruption wording gets both retrieval and
CLEAR acceptance. Exact names and both complementary-source requests already
work, so a general retrieval rewrite is unjustified here.

A separate Phase 3 evaluation should freeze a larger independently labeled corpus,
run the actual PostgreSQL identity/query/ranking path on a disposable target, and
compare a bounded lexical expansion candidate approach with an optional offline
semantic candidate seam. Report held-out synonym recall, exact-mechanic retention,
edition/game contamination, currentness, source revision/provenance, authority
negatives, grounded final-answer coverage, latency and resource cost. Candidate
similarity must never supply missing acquired identity or semantic claim support.
No semantic infrastructure or model dependency is introduced or enabled here.
